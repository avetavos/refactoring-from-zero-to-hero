## จุดประสงค์

ดึงชิ้นส่วนหนึ่งของ expression ก้อนใหญ่มาเก็บไว้ในตัวแปร local ที่ตั้งชื่อดี ๆ แล้วใช้ชื่อนั้นแทน sub-expression เดิม อีกชื่อที่คุ้นหูคือ Introduce Explaining Variable

## Code Smell

นี่คือวิธีรักษา **cryptic one-liner** คือ expression ที่แน่นจนต้องแกะในหัวใหม่ทุกครั้งที่อ่าน เงื่อนไข boolean ที่ถักจากการเปรียบเทียบสามชั้น หรือสูตรราคาที่เต็มไปด้วยเลขคณิตปริศนา ล้วนซ่อนความหมายไว้หลังเครื่องหมายวรรคตอน พอตั้งชื่อให้แต่ละส่วน บรรทัดนั้นก็กลายเป็นอะไรที่อ่านออกเสียงได้เลย

## ก่อน → หลัง

การตรวจเงื่อนไขจัดส่งอัดความหมายทั้งหมดไว้ใน boolean expression บรรทัดเดียว พอตั้งชื่อให้แต่ละส่วน กฎที่ซ่อนอยู่ก็โผล่ออกมา

## กลไกการทำงาน

1. เช็กก่อนว่า sub-expression ไม่มี side effect เพราะการ extract ชิ้นที่ไปแก้ state อาจเปลี่ยน behavior ได้
2. ประกาศตัวแปร local แบบ immutable แล้วกำหนดค่า sub-expression ลงไป
3. ตั้งชื่อที่บอกว่าค่านั้น *หมายถึงอะไร* ไม่ใช่บอกว่าคำนวณมายังไง
4. แทนที่ sub-expression เดิมด้วยตัวแปรใหม่
5. **รัน test**
6. ถ้า sub-expression เดียวกันโผล่หลายครั้งใน scope นั้น ให้แทนที่ให้ครบทุกจุดแล้ว test อีกรอบ

## ใช้เมื่อไหร่ / ข้อแลกเปลี่ยน

ใช้ตอน debug ได้ดี เพราะตัวแปร local ที่มีชื่อจะส่องดูค่าง่าย นอกจากนี้ยังช่วยหั่นสูตรยาว ๆ ออกเป็นชิ้นที่ review ไหว และทำให้เงื่อนไขอธิบายตัวเองได้ ถ้าใช้อยู่ใน function เดียว ตัวแปร local ก็พอแล้ว แต่ถ้าคำอธิบายชุดเดียวกันมีประโยชน์ทั้ง object ให้ไปทาง **Replace Temp with Query** หรือ extract เป็น method แทน

ฝั่งตรงข้ามคือ **Inline Variable** ถ้าชื่อตัวแปรไม่ได้เพิ่มอะไรจาก expression ที่เก็บอยู่ ก็เอา expression ใส่กลับเข้าไปแล้วลบตัวแปรทิ้ง

## เนื้อหาที่เกี่ยวข้อง

- [Replace Temp with Query](/refactoring/th/composing-methods/replace-temp-with-query/)
- [Extract Function](/refactoring/th/composing-methods/extract-function/)

| ใช้ Extract Variable เมื่อ | หลีกเลี่ยงเมื่อ |
|---|---|
| expression ซับซ้อนจนต้องอ่านหลายรอบ | ชื่อที่คิดได้ไม่ได้อธิบายดีกว่า expression เดิม |
| condition มีหลาย operand — `a && b && !c` | ต้องการ expression นั้นใน function อื่น — Extract Function แทน |
| magic number ที่ไม่รู้ว่าหมายถึงอะไร | variable ใช้แค่ครั้งเดียวและ expression สั้น |

> ⚠️ ไม่ควร Extract Variable เมื่อ:
> - expression ง่ายอยู่แล้ว — `x + 1` ไม่ต้องการชื่อ
> - ต้องการใช้ logic เดิมในหลายที่ — Extract Function ดีกว่า
> - กำลังสร้าง variable แบบ `temp` หรือ `result` ที่ไม่บอกอะไร

<Callout title="สิ่งที่ตรงกันข้าม: Inline Variable">
Extract Variable เพิ่มชื่อเข้าไป ส่วน Inline Variable เอาชื่อที่ไม่คุ้มออก ถ้าเจอ `const x = order.total` แล้ว `x` ถูกใช้แค่ครั้งเดียวถัดลงมาทันที ชื่อนั้นก็เป็นแค่ noise ควร inline ทิ้งไปเลย ชื่อควรแลกมาด้วยความชัดเจน ไม่ใช่แค่พิธีกรรม
</Callout>
